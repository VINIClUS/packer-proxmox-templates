## SDN Permission Retry

After `SDN.Use` was granted on `/sdn/zones/localnetwork/vmbr0`, Packer created
and started VM `9101`, uploaded the generated answer ISO, and reached the
Windows installer.

Console validation showed the first installer blocker was:

```text
Install driver to show hardware
```

The VM had the Windows and VirtIO ISOs attached as SCSI CD-ROMs:

```text
boot  : order=scsi1;ide0;scsi0
scsi1 : local:iso/win11_24H2_english_x64.iso,media=cdrom
scsi2 : local:iso/virtio-win.iso,media=cdrom
```

The template now attaches both installer media ISOs as SATA CD-ROMs and boots
with `order=sata0;ide0;scsi0`, keeping the system disk on VirtIO SCSI.

The next console validation passed the media-driver screen and reached the
Windows product-key page. The answer file now injects `windows_product_key`
so setup can remain unattended.

The following retry passed the product-key page and stopped at image selection.
Console validation showed the uploaded ISO contains:

```text
Windows 11 Enterprise
Windows 11 IoT Enterprise
Windows 11 IoT Enterprise Subscription
```

The template defaults now target `Windows 11 Enterprise` and use the public
Windows 11 Enterprise setup key. This key does not activate Windows.

The next retry passed image selection and stopped at Windows 11 system
requirements:

```text
The PC must support TPM 2.0.
```

The template now adds `tpm_config` with `tpm_version = "v2.0"` and stores TPM
state on the configured VM storage pool.

After TPM was enabled, OVMF initialization delayed the Windows ISO boot prompt
enough that the original two-space `boot_command` could miss the prompt. The
template now repeats the spacebar keypress for several seconds after
`boot_wait` to reliably enter Windows Setup.

The next retry reached the specialize phase and displayed the
`Configure-WinRM.ps1` command, but setup did not continue. The WinRM script now
runs with `-NoProfile -NonInteractive`, emits progress messages, starts WinRM
without restarting it, and avoids a synchronous `Restart-Service` call during
Windows setup.

The following retry showed the script hanging immediately after its first
progress line, before WinRM service setup. The script no longer calls
`Get-NetConnectionProfile` or `Set-NetConnectionProfile` during specialize;
the firewall rule already uses `Profile Any`.

The next retry reached the Windows desktop, but Packer still waited for WinRM
and the console showed no active network path. `Configure-WinRM.ps1` now scans
mounted media for `NetKVM\w11\amd64\netkvm.inf`, installs it with `pnputil`,
renews DHCP, and then starts/configures WinRM.

The following retry confirmed NetKVM installed and DHCP assigned an IPv4
address, but installing `guest-agent\qemu-ga-x86_64.msi` during specialize
hung setup. QEMU Guest Agent installation remains in the post-WinRM
`Install-VirtIO.ps1` provisioner; the pre-WinRM script now only installs
NetKVM, renews DHCP, and configures WinRM.
