The following retry showed the script hanging immediately after its first

The next retry reached the Windows desktop, but Packer still waited for WinRM
and the console showed no active network path. `Configure-WinRM.ps1` now scans

The following retry confirmed NetKVM installed and DHCP assigned an IPv4

## Guest Agent ACL Retry

After `VM.GuestAgent.Audit` and `VM.GuestAgent.Unrestricted` were granted,
Packer no longer received a 403 from the guest-agent API. The next debug build
instead reported:

```text
500 QEMU guest agent is not running
```

That is expected before post-WinRM provisioning installs the guest tools. A
temporary explicit `winrm_host` test showed direct WinRM attempts, but the
build VM address is not stable without a fixed MAC/DHCP reservation. The
template now includes `Install-QemuGuestAgent.ps1` on the generated answer ISO
and runs it as the first first-logon command. That installs and starts QEMU
Guest Agent after OOBE, allowing Proxmox to report the actual guest IP before
Packer connects over WinRM.

The next diagnostic retry confirmed the Proxmox VM has `agent: 1` and Windows
shows the `QEMU-GA` service running, but Proxmox still returns:

```text
500 QEMU guest agent is not running
```

That means the API ACL issue is cleared, but the guest-agent service cannot
communicate through the VirtIO serial channel yet. The first-logon installer now
installs `vioserial\w11\amd64\vioser.inf` with `pnputil` before installing and
starting `guest-agent\qemu-ga-x86_64.msi`.

The following live diagnostic reached `192.168.1.49:5985`, but WinRM returned
`401 - invalid content type`. Guest-agent diagnostics showed the Administrator
account was active and Basic auth was enabled, but `AllowUnencrypted` remained
`false` because Windows kept the NIC on a Public network profile. The
first-logon installer now changes Public profiles to Private and reapplies
`winrm/config/service AllowUnencrypted=true` after OOBE, avoiding the specialize
hang risk from network profile cmdlets.

The next clean retry still reached the guest IP but returned intermittent 401s
and then stopped before provisioning. The first-logon step now waits for a
network profile to exist, runs `Enable-PSRemoting -SkipNetworkProfileCheck`,
sets `LocalAccountTokenFilterPolicy=1`, and then reapplies
`AllowUnencrypted=true` before Packer's WinRM connection stabilizes.

The following debug build connected to WinRM and started the first PowerShell
provisioner, then lost `192.168.1.125:5985` while uploading the provisioner
environment script. This confirms the guest-agent ACLs and WinRM authentication
are no longer the active blockers; the remaining issue is a readiness race
immediately after the first reachable WinRM probe. The template now sets
`pause_before_connecting = "2m"` so Packer performs the first reachability
check, disconnects, waits for Windows networking and WinRM to settle, and only
then reconnects for provisioning.

The next retry verified that pause: Packer reconnected after the delay and ran
both `Install-VirtIO.ps1` and `Optimize-Template.ps1`. The build then failed
because Windows refused to clear the protected

## Enterprise Remote Management Additions

The template now attaches Proxmox `serial0` as a socket with
`serials = ["socket"]` and runs `Configure-EnterpriseRemoting.ps1` before
template optimization. The script enables Windows EMS/SAC on COM1 at 115200
baud, installs the native `OpenSSH.Server` Windows capability, starts and
auto-enables `sshd`, sets `HKLM:\SOFTWARE\OpenSSH\DefaultShell` to PowerShell
with a PowerShell 7 preference when present, and ensures inbound TCP 22 is
allowed. These settings provide a headless break-glass console path and a
standard SSH automation transport alongside the existing WinRM build channel.

The first validation build after adding `serial0` reached the initial WinRM
probe, then Proxmox reported `500 QEMU guest agent is not running` during the
post-pause reconnect. `Install-QemuGuestAgent.ps1` now configures Windows
Service Control recovery for `QEMU-GA` with three 5-second restart attempts, so
the guest-agent channel can recover during first-logon device settling.

The next validation build reached the new `Configure-EnterpriseRemoting.ps1`
provisioner and successfully applied both EMS `bcdedit` commands, then failed
while installing the OpenSSH Windows capability:

```text
Add-WindowsCapability : Access is denied.
```

That command requires an elevated PowerShell session. The Windows PowerShell
provisioners now set `elevated_user = var.winrm_username` and
`elevated_password = var.winrm_password`, so DISM-backed capability
installation runs through Packer's elevated scheduled-task path instead of the
default non-elevated WinRM shell.

The elevated retry installed `OpenSSH.Server` successfully and reported
`RestartNeeded : False`. The same run then exposed a firewall compatibility
issue on Windows 11: `Set-NetFirewallPortFilter` does not accept
`-AssociatedNetFirewallRule` in this environment. The SSH firewall block now
removes the named `OpenSSH-Server-In-TCP` rule when present and recreates it
with TCP 22, which is deterministic and avoids version-specific mutation
parameters.
